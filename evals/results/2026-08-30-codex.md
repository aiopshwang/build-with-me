## 스파이크에서 확인한 사실

환경: `codex-cli 0.150.0`, Windows 11, Git Bash. 워크스페이스는 레포 바깥 `/c/tmp` 아래
(커밋 대상 아님).

- `codex login status` → `Logged in using ChatGPT`, 실제 턴도 정상 동작(이전 시도의
  "refresh_token_invalidated" 인증 실패는 재현 안 됨 — 그 사이 재로그인된 것으로 보임).
- 이벤트 타입: `thread.started`(스레드 시작, 이후 매 턴마다 같은 `thread_id`로 다시 나옴) →
  `turn.started` → `item.started`/`item.completed`(`item.type`이 `agent_message` 또는
  `command_execution` 또는 `file_change`) → `turn.completed`. 실패 시 `error` / `turn.failed`.
- 최종 assistant 메시지: 그 턴의 `item.completed` 이벤트 중 `item.type == "agent_message"`인
  것의 **마지막 것**의 `item.text` (한 턴 안에 명령 실행 사이사이 여러 번 말하기 때문에 마지막
  것만 그 턴의 "마지막 말").
- `codex exec resume --last --json --skip-git-repo-check "..."`은 세션을 이어간다 — 직접
  확인: 1턴째 "안녕, 한 줄만 답해줘" → "안녕하세요! 무엇을 도와드릴까요?", 2턴째
  "방금 뭐라고 했지?" → 그 문장을 정확히 인용해 답함(같은 `thread_id`).
- **`codex exec resume`에는 `-s`/`--sandbox` 플래그가 아예 없다** — `codex exec --help`엔
  있지만 `codex exec resume --help`엔 없다. 직접 실행해 확인: `-s danger-full-access`를 붙이면
  `error: unexpected argument '-s' found`로 즉시 실패한다. 두 서브커맨드 모두에 있는
  `--dangerously-bypass-approvals-and-sandbox`(=샌드박스·승인 프롬프트 모두 생략, `-s
  danger-full-access`와 동등)로 대체해 첫 턴·재개 턴 모두에 통일해서 썼다. 이건 실제 2런을
  돌리기 전 `agent_argv()`에서 잡아낸 버그이며, 고쳐서 커밋했다(아래 "구현 중 발견한 버그").
- 스킬 로드 흔적: 워크스페이스에 `.agents/skills/build-with-me/`를 미리 복사해두면, 실행
  이벤트 중 `command_execution` 항목의 `command` 필드에 `Get-Content -Raw
  '...\.agents\skills\build-with-me\SKILL.md'` 같은 PowerShell 명령이 그대로 찍힌다 —
  Codex는 전용 Skill 도구가 없고 파일을 셸 명령으로 직접 읽는다. `skill_invoked_codex()`는 이
  명령 문자열에서 `build-with-me`와 `SKILL.md`를 같이 찾으면 `True`, 못 찾으면 `None`(모른다
  — "명령이 안 보였다"가 "안 읽었다"의 증거는 아니므로).
- 네트워크: `workspace-write` 샌드박스는 아웃바운드 네트워크를 막는다 — 직접 확인:
  `git ls-remote https://github.com/...`가 41ms만에 연결 실패. `danger-full-access`에서는
  같은 명령이 성공(실제 리포 HEAD 커밋 해시를 정확히 받아옴). 배포 게이트가
  `gh repo create`/`git push`로 네트워크를 쓰므로, 두 런 모두 **`danger-full-access`**로
  돌렸다(`--sandbox` 기본값도 이걸로 바꿔뒀다).

## 구현 중 발견한 버그 2건 (실런에서 드러남)

1. **`codex exec resume`의 `-s` 부재** — 위 스파이크 절 참고. `--dangerously-bypass-
   approvals-and-sandbox`로 교체.
2. **`count.py`의 "걸음 수"(`git commit` 카운트)가 Codex 런에서 0으로 나옴** — Codex가 실행한
   실제 명령은 `git -c user.name='Build With Me' -c user.email='...' commit -q -m '...'`였다
   (git 전역 identity가 없는 샌드박스라 매 커밋마다 `-c`로 직접 넣음). 기존 코드는 `"git
   commit" in x` 단순 부분 문자열 검사라 `git`과 `commit` 사이에 `-c ...` 플래그가 끼면 못
   잡았다. `GIT_COMMIT_RX = re.compile(r"\bgit\b[^;\n|&]*?\bcommit\b")`(같은 셸 문장 안에서
   `git`부터 `commit`까지, `;`/`|`/`&`로 다음 문장으로 못 넘어가게)로 교체 — `git push`를 찾는
   `DEPLOY_RX`도 같은 이유로 동일하게 고쳤다. 고치기 전/후로 `survey` 런의 "걸음 수"가 0 → 3으로
   바뀌는 것으로 직접 확인.

## 무엇을 측정할 수 없었는지(Codex 자체의 한계)

- **`skill_invoked`가 삼상(true/None)** — Codex엔 Claude Code 같은 전용 Skill 도구가 없어
  "명령 문자열에 SKILL.md 읽기가 찍혔는지"로만 판단한다. 이번 두 런은 둘 다 찍혀서 `true`였지만,
  구조적으로 "찍히지 않음"이 "안 읽음"의 증거가 될 수 없어 그 경우는 `false`가 아니라
  `None`으로 남긴다(브리프 지시대로).
- **`공개 직전 네 질문`이 두 런 다 None** — count.py 자체는 두 호스트에서 동일하게 동작하지만
  (`_deploy_window`가 `blocks()`를 통해 Codex의 `command_execution`도 읽는다), 두 런 모두
  실제 대화가 배포 명령(`gh repo create`/`git push`) 전에 끝나서 잴 대상이 아예 없었다 — 이건
  호스트 차이가 아니라 이번 두 런의 진행 길이 문제다.
- 그 외 count.py의 모든 행(첫 화면 턴·질문 수·식별자·걸음 수·확인 질문 비율·기록 대사·선택지
  매트릭스·코드 덤프·해도 될까요·파일·내-말로 문장수/기술용어)은 `blocks()` 어댑터 하나로 두
  호스트 모두에서 측정된다 — Codex 전용 예외 처리를 count.py에 따로 두지 않았다.
